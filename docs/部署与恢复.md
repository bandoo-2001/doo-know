# 部署与恢复

这些是可审查的模板与操作说明。当前只运行本机隔离示例预览；真实知识库接入、常驻服务与公网发布尚未执行。

## 发布与权限

1. 选择已验证的源码版本，将构建产物和锁定依赖发布到 `/srv/stacks/knowledge/doo-know-web/releases/<明确版本>/`，`app` 链接指向当前版本。回滚可把链接切回上一个版本。不要直接引用开发工作目录。
2. 数据在 `/srv/data/knowledge/doo-know-web/`，密钥与受控配置在 `/srv/secrets/knowledge/doo-know-web/`。目录由运行用户访问（建议 700），密钥文件 600，不使用 777。
3. 当前主机模板使用 bandoo 用户、端口 3010、回环绑定。按实际运行用户调整所有权、systemd 的 ReadWritePaths 以及 Compose 的 UID/GID。只开放所选原文目录与独立数据目录的写权限。
4. 认证密钥在受控目录本机生成，内容不通过参数或日志传递。`AUTH_SECRET_FILE` 指向该文件；密钥长度至少 32 字符。生产必须明确配置 KNOWLEDGE_ROOT、DATA_ROOT、AUTH_SECRET_FILE、APP_ORIGIN。
5. 在本机交互终端运行 `npm run account -- init` 创建唯一账号。生产配置无注册；遗忘密码用 `npm run account -- reset`，旧会话全部失效。

### 进程部署

使用 [systemd 模板](../deploy/doo-know-web.service)，工作目录为已发布 app，EnvironmentFile 位于受控目录。模板 ReadWritePaths 中列出的真实知识库路径只是部署声明，不表示已接入。启用前按选定库调整并检查权限和已有端口。日志使用 journald，不记录请求 URL、正文、Cookie 或分享令牌；沿用主机已有保留策略。

### 容器部署

[Dockerfile](../deploy/Dockerfile) 通过同一 Node 22 基础镜像构建依赖和产物；[Compose](../deploy/compose.yaml) 将知识库、数据、密钥分开挂载。配置文件中的容器路径只在容器内使用，不替代主机目录约定。服务以非 root UID/GID 运行，根文件系统只读，端口仅发布到回环地址。

如部署位置改变 Compose 文件，应同时发布对应 Dockerfile 和构建源码，或把 build 改为已构建镜像标签。Compose 模板只是源仓库内可构建示例。构建产物包括可直接用 Node 运行的管理 CLI，生产镜像不依赖 tsx：

```bash
docker compose -f deploy/compose.yaml exec notes npm run account:prod -- init
docker compose -f deploy/compose.yaml exec notes npm run account:prod -- reset
```

备份和恢复需要暂停 notes 服务及外部编辑。为一次性容器显式挂载受控备份目录，使用同一 UID/GID、同一数据挂载与生产环境变量：

```bash
docker compose -f deploy/compose.yaml stop notes
docker compose -f deploy/compose.yaml run --rm --no-deps -v /srv/backups/doo-know-web:/backups notes npm run backup:prod -- /backups/<唯一名称>
# 恢复前，将 Compose 的原文与数据挂载改为新的空目标目录。
docker compose -f deploy/compose.yaml run --rm --no-deps -v /srv/backups/doo-know-web:/backups:ro notes npm run restore:prod -- /backups/<备份名称>
```

未在此主机实际构建容器镜像；编译后的 CLI 入口已在本机直接运行验证。

### HTTPS

使用主机现有 HTTPS 反向代理；[Caddy 模板](../deploy/Caddyfile) 提供域名与反代声明。APP_ORIGIN 必须与浏览器访问来源完全一致。不要开放 Vite 或直接公网暴露开发服务。代理若已有访问日志，应避免记录包含分享令牌的 URL。

## 一致性备份

备份必须同时保护原文（包括附件和回收站）、SQLite 和 history。Git 不能替代此备份。

暂停应用进程及外部编辑器/AI 的写入，再执行：

```bash
cd /home/bandoo/workspace/projects/doo-know-web
npm run backup -- /srv/backups/doo-know-web/<本次唯一名称>
```

父目录需要存在，目标目录必须尚不存在。脚本使用 better-sqlite3 `backup()` 生成 SQLite 一致性副本，复制原文和历史，并生成 SHA-256 校验清单；原文在复制期间变化会报错。它拒绝软链接和共享硬链接，避免越界复制。失败备份不能作为唯一恢复来源，保留现场并选新目录重试。

暂停服务是原文与元数据同一时点的保障；SQLite 在线备份本身不保证外部 Markdown 同时一致。密钥不进入普通备份，使用受控加密方式单独备份。备份目录本身受限访问。另存独立设备或异地，并定期演练恢复。

## 恢复

停止应用。设置目标 KNOWLEDGE_ROOT 与 DATA_ROOT，两个目录必须为空；保留旧目录作为回退，不就地覆盖原文。AUTH_SECRET_FILE 使用受控恢复的密钥或新生成密钥。

```bash
npm run restore -- /srv/backups/doo-know-web/<已验证备份名称>
```

脚本校验全部文件，恢复原文、附件、回收站、SQLite 和 history，运行 SQLite integrity_check，删除全部旧 session 并禁用全部 share，同时登记机器令牌发行时间截止。清除派生快照/全文/向量，保留未结束操作的核对证据并提升原文版本，后续 worker 重建索引。主人重新认证后验证目录、原文、恢复记录和代表性检索，再重新生成确需公开的链接。恢复途中失败保留已复制内容供排查，不能把部分恢复目录当作成功结果；重新演练使用新的空目标。

隔离恢复演练由 `tests/backup.test.ts` 实际执行：确认 CRLF 字节、最新正文、旧历史、账号登录可用、旧会话失效与旧分享 404。未用真实资料执行破坏性测试。

新增索引与远程令牌恢复验证见 `tests/knowledge/restore-index.test.ts`；完整运行顺序、模型空间切换和限额见 [MCP 与本地索引运维](MCP与索引运维.md)。Node 容器模板不包含 CPU Python/model，默认关闭索引，完整检索使用 native 配置；当前主机未构建 Docker 镜像。

## 故障处理

- 保存失败：页面保留编辑内容，不标记为已保存。检查原文目录、history 目录、磁盘余量和运行用户权限；修复后重新保存，版本变化仍需确认。
- 409 冲突：取消保留输入；查看最新原文，再决定是否覆盖。再次变化再次确认。
- 401：重新登录后继续当前编辑，不把草稿持久化到浏览器；保存仍重新比较文件时间。
- 原位置占用：回收站恢复选择新文件名，不覆盖当前文件。
- 旧分享 404：可能已取消、重置、删除或原文不再存在。扫描发现外部重命名视为旧文件离开、新文件加入，新文件默认私有。
- 忘记密码：本机交互重置，撤销所有旧会话。修改密码不会自动恢复已经停用的分享。
