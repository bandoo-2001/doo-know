# To Doo MCP coverage

The adapter covers the current business surface in `shared/to-doo-contracts.ts` and all four To Doo route modules. It reuses the portable command, attachment, import/calendar, notification and durable outcome-note engines. It does not call a browser-owner API or accept a filesystem path for an import/attachment.

`R` = `to-doo:read`; `W` = `to-doo:write`; `S` = explicit `to-doo:share`; `I` = explicit `to-doo:integrations`; `KR/KW` = knowledge read/write. Each invocation also enforces the live list resources, configured list selectors and content domains. A new sharing or integrations action is never inferred from an old read/write grant.

`describe_to_doo_schema` publishes paged command/entity catalogs and complete JSON field schemas. `save_to_doo_entity` uses strict create fields or strict optional patch fields; patch defaults never reset omitted values. Feed, source and import-history metadata/lifecycle additionally require their explicit sharing/integrations rights; internal outcome operations remain reserved to the durable workflow. `execute_to_doo_command` validates the shared command schema. Its catalog routes attachments, imports and internal workflow records to their dedicated tools. The original nine tools remain available, including `manage_to_doo` and its now-explicit discovery instructions.

## Entity coverage

Every public entity has `query_to_doos(kind=...)` for bounded summary reads, including long-text field pages. `read_to_doo_entity` retrieves the complete authorized entity as JSON pages under `to-doo:read`, including large arrays. Pages bind the entity revision and the sanitized content hash; omitted knowledge references remain omitted and internal workflow records stay on their dedicated caller-bound route. Ordinary creation/update uses `save_to_doo_entity`; lifecycle uses the shared `delete_entity` command (including restore and cascade with expected revision).

## Recovery, transfer and limits

Read-only clients can inspect all ordinary large structured values without a sharing grant: obtain the revision from `query_to_doos`, then join `read_to_doo_entity` content pages using `range.nextOffset` and pass the returned `sha256` as `expectedContentHash`. Current entity/list/content/note rights are rechecked on each page, and every complete JSON-RPC frame is measured before returning.

Shared task command receipts remain available through `query_to_doos(receiptRequestId=originalRequestId)`. Dedicated adapter action receipts use `get_to_doo_operation` and original request identity; pending writes remain pending rather than being duplicated. Outcome notes have a caller-bound durable operation and `get_to_doo_outcome_operation`, including optional revision-bound UTF-8 draft pages. Completed operations discard their draft; the saved note remains available through knowledge reads. Note creation reuses the actual caller principal rather than web-owner privileges.

Imports/exports/attachments use the common opaque transfer engine: declared byte counts/hash, bounded chunks, caller/client/library identity, live authorization and source revisions, expiration and safe finalization. Attachment finalization and durable import preview claim the upload’s immutable request identity before any domain side effects. Export downloads bind the dataset revision and recheck every included note identity/workflow path; moving a referenced note outside the knowledge grant invalidates the download. Import-preview downloads also reauthorize their original preview before each transfer read. A scoped JSON export excludes unrelated lists, content domains, internal operations, source integration state, transactions and receipts. A full checkpoint is an explicit separate request with complete list/content-domain access and knowledge-reference checks. Explicit protected checkpoint restoration uses one shared checkpoint transaction so adopting the source dataset identity cannot strand an import between authorized batches. A restored dataset identity can require a newly selected grant for later calls. Protected ordinary background imports persist their authorization requirement and stop if permission changes or a restarted process has no reattached live authorization guard.

All tool input and output schemas are registered through the SDK. Discovery pages and complete JSON-RPC replies keep the existing 64 KiB frame budget, and incoming requests keep the existing 128 KiB limit. Catalogs, feeds/connections/devices, entity reads, draft content and transfer content use bounded pages. Existing nine-tool compatibility, agent-port authorization, import/attachment/notification engines and the full SDK regression are run together by the parent verification pass.

## Notification scheduler follow-up (2026-10-31)

The HTTP/UI notification runtime and MCP administration still share the core notification engine. Its domain reader now reuses a full entity snapshot only while the dataset and immutable transaction head match, preserving store.refresh and live per-event time checks. A sequence index supports version lookups. Device state and host activation remain live; no authorization scope, external tool, wire schema or portable format is broadened. Legacy adapters without the optional internal getVersion method retain uncached reads. Cross-connection commands, midnight, source changes during network waits, device revocation and host deactivation have targeted regressions; 52 related files/457 cases pass. The old native-recovery skip attribution was corrected; 15 native recovery cases now pass. Actual user-device delivery remains manual and no live MCP deployment occurred.
