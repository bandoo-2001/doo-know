# Blog business coverage through MCP

All management routes in `apps/server/blog/routes.ts` use the existing blog service. The named MCP tools call that service through an optional `blogTools` host port. Public page routes remain available at their existing URLs; MCP exposes their underlying settings, article, version and resource data through authorized management reads.

Every tool requires `knowledge:read` and `blog:read`. Article reads and writes additionally require the current source-note path grant and the selected article or site grant. Site settings and creating a new article require a site/all grant. A selected article with `manage` can delete that article; it cannot administer the site. New `blog:write` and `blog:manage` actions are independently granted. Existing read/publish and legacy knowledge-write grants gain neither action.

## Blog studio

| Studio capability | Named MCP tools | Authority and bounds |
| --- | --- | --- |
| Read complete draft/published configuration and retained history | `get_blog_design` | Site `blog:read`; choose `kind`, reconstruct `json` using `nextByte` and UTF-8 `offset`, verify `byteLength`/`sha256`; each page ≤8192 bytes. Version, draft/published hashes and up to ten history entries accompany each page. Restart reading if version changes. |
| Save decoration draft | `update_blog_design` | Site `blog:manage`, required `expectedVersion` and `requestId`; pass either `designJson` (≤24000 UTF-8 bytes) or `designTransferId`, never both. Uses the same strict design validation and media-reference checks as the browser. |
| Publish draft / restore historical revision into draft | `publish_blog_design`, `restore_blog_design` | Site `blog:publish` / `blog:manage`; CAS plus exact-input idempotency. Restore does not publish. All mutations return summary hashes/lengths/history rather than full configuration. |
| Upload complete large configuration | `begin_blog_design_upload(kind=design)` then `append_mcp_upload`, then `update_blog_design` | Site `blog:manage`; declare current design version, SHA-256, byte length, name and `application/json`; ≤16MiB and valid UTF-8 JSON. |
| Upload avatar/cover media | `begin_blog_design_upload(kind=media)` then `append_mcp_upload`, then `commit_blog_design_media` | Site `blog:manage`; ≤5MiB PNG/JPEG/WebP, real signature and SHA-256 verification. `mcp-blog-studio.test.ts` exercises full Unicode reconstruction, large transferred drafts, media validation, stale/cancelled/expired uploads, original-input replay after later revisions or expired staging, scope revocation, selected-post rejection, diagnostics paging, legacy reserved-slug republishing, and real MCP SDK discovery/calls. It measures the complete duplicated MCP result frame, including an escaped 128-character request ID.

Studio transfers bind the site identity and current **design** version (independently of site-settings version). Every generic chunk/status operation reauthorizes current site management rights; commit rechecks the binding and fresh authority. Completed operations replay their persisted receipt only for the identical request/input, so version drift or expired staging cannot cause duplicate writes. Changed input/request, stale unfinished uploads, cancellation and expiration reject commits. Legacy scope grants remain unchanged and selected-post grants cannot read or administer whole-site design.

## Transfer and size behavior

Tool schemas reject extra fields. Inline results omit Markdown, HTML and binary bodies. Article details retain bounded metadata with `truncatedMetadata` markers; complete metadata is available as a JSON transfer. Lists dynamically reduce the number of items to fit response budgets and return continuation. Settings about text uses UTF-8 boundaries. Resource and content transfers use the canonical `McpTransferInfo` DTO and generic chunk tools; identifiers never accept host filesystem paths.

Transfers bind principal, client, article or site identity and current revision. Each chunk access rechecks the associated domain authorization through `authorizeTransfer`; preview resources also recheck linked resource access. Diagram sources bind the current fence and source hash, including referenced whiteboard changes. PNGs use the existing publication capture and PNG-validation pipeline. Uploads do not write notes, publish a snapshot, or enable the site. Their explicit final operation records a stable receipt before returning.

Browser rendering, public HTML navigation, CSS, RSS/XML serialization and existing public URLs remain presentation surfaces. MCP does not need a second website renderer: it exposes the complete authorized business data and immutable rendered article content used by those surfaces.

Missing-diagram discovery returns the full truthful count and accepts every nonnegative continuation offset, with at most twenty needs per page. The separate publication operation retains its explicit limit of sixty-four supplied previews and twenty MiB of preview bytes. A source having more needs can still be inspected completely.

Immutable version reads expose `coverResource` as either `null` or `{postId, versionId, hash, mime, sizeBytes}`. The editable `metadata.cover` reference remains available separately. Complete `version_metadata` JSON preserves all original metadata fields and adds the same strict `coverResource` binding. The host verifies that the cover hash belongs to the requested article/version resource relation, and transfers recheck the current article/source grant even when the original cover file changes or the site is disabled.
