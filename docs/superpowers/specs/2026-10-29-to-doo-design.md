# To Doo 第一版设计方案

历史讨论，已由[全量功能设计方案](2026-10-29-to-doo-full-design.md)取代；不作为当前实施范围。

日期：2026-10-29

状态：待用户确认的设计稿；本文件不代表功能已经实现或部署。

## 1. 定位与已确认方向

To Doo 是 DooKnow「应用」中的第二个原生子应用，提供与知识库联动的个人任务与日程管理。核心体验是：围绕一个目标找到资料、安排下一步行动，完成后留下可再次使用的记录。

用户已经确认的方向：

- 保留清单、任务、日程等通用能力，适用于学习、工作与生活。
- 差异化重点是目标、笔记、白板、任务和成果之间的联系。
- 长期用户数据保存到所绑定知识库根目录的 `_data/apps/to-doo/`，随知识库 Git 同步和迁移。
- SQLite 承担本机查询、投影和运行状态；应用内容能够从便携文件恢复。

以下首版范围、交互细节和格式约束是本方案的建议，尚待确认，不视为用户已经逐项批准。

### 1.1 方案比较

| 方案 | 收益 | 代价与适用性 | 本方案选择 |
| --- | --- | --- | --- |
| 通用效率工具全集：任务、所有视图、习惯、专注、纪念日同时建设 | 一次覆盖更多使用场景 | 首版面广；笔记联动与数据可靠性容易被摊薄 | 保留作为长期功能池，分期建设 |
| 围绕目标组织任务、资料和成果，配齐常用视图 | 能发挥现有知识库与白板的作用，同时满足日常待办 | 需要明确笔记身份、进度和记录的语义 | 用户已认可该方向，本方案据此展开 |
| 以 AI 自动拆解和自动排程为主要入口 | 输入目标即可获得计划建议 | 需要新的任务授权与模型连接；建议质量和执行边界需要单独验证 | 后续增强，首版基础操作独立可用 |

### 1.2 成功标准与边界

首版应能完成这样一条流程：创建「系统架构师备考」目标，分章节建立任务，关联笔记或白板，把本周要做的任务安排进日历，完成后保留结论和成果，换一台机器同步整个知识库后恢复这些内容。

普通事项如买东西、缴费、预约，可以直接新建和勾选，无须先建立目标或填写成果。

首版沿用当前平台的单主人、单知识库和在线网页使用方式。同一服务上的手机和电脑共用服务端数据；独立服务器之间通过既有 Git/文件同步流程迁移，不提供实时多人协同或多主机自动合并。

## 2. 首版功能范围

| 功能 | 首版行为 | 边界 |
| --- | --- | --- |
| 快速收集 | 收集箱、一行创建、快捷日期选择；标题提交即可创建 | 中文自然语言日期识别和语音输入后续建设 |
| 任务管理 | 标题、Markdown 备注、优先级、标签、状态、预计分钟数、排序 | 备注不支持执行 HTML、脚本或自动抓取外部链接 |
| 子任务 | 折叠大纲、父子关系、同清单内调整层级 | 最多 8 层；不能成环；首版不批量完成整棵子树 |
| 清单与目标 | 普通清单和目标清单；清单内章节分组；目标可写说明、目标日期和完成标准 | 目标是带附加信息的清单，不另建一套重复任务模型 |
| 常用入口 | 收集箱、今天、未来七天、逾期、未安排、已完成、回收站；关键词、标签、状态过滤 | 不提供自定义查询语言或复杂过滤器编辑器 |
| 日期安排 | 独立的计划日期、可选时间与时长，以及独立的截止日期/时间 | 目标日期不会自动成为所有任务的截止日期 |
| 简单重复 | 每日、每周指定星期、每月指定日期，可设间隔和结束日期 | 固定日历周期；不含农历、法定工作日、完成后 N 天或复杂 RRULE |
| 提醒 | 服务端持久调度、站内提醒中心、错过提醒汇总、确认/忽略/稍后提醒 | 必达范围是恢复访问后可看到提醒记录；关闭网页的手机推送不在首版承诺内 |
| 笔记与白板联动 | 手动关联已有资料；从笔记选中文字或勾选项创建任务；返回来源 | 不自动扫描全部勾选框，不自动双向修改正文 |
| 完成标准与成果 | 可选完成标准、成果笔记/白板关联；完成时可补一句结果 | 不强制提交成果，不把打勾等同于已经掌握知识 |
| 进展记录 | 对目标或任务写进展、疑问、下一步，可选填写本次投入分钟数 | 手工记录；不提供番茄计时和自动工时推断 |
| 数据与迁移 | 保存到 `_data`、格式校验、冲突提示、回收站恢复、整库 Git/备份迁移 | 不同步运行中 SQLite；不自动提交或推送 Git |

首版不包含四象限、甘特式时间线、习惯打卡、番茄钟、倒数纪念日独立模块、第三方日历订阅、滴答清单导入、共享指派与任务 MCP 工具。这些功能不需要为首版提前创建空数据目录或模拟界面。

## 3. 展示模式与操作

所有模式使用同一份任务数据。切换视图只改变呈现、筛选或排序，不复制任务。

| 模式 | 用途 | 首版内容与操作 |
| --- | --- | --- |
| 目标总览 | 看清一个目标的整体情况 | 说明、目标日期、叶子任务进度、本周安排、阻塞事项、相关资料、最近进展与成果；普通清单也可使用简化总览 |
| 列表/大纲 | 收集、分解和逐项推进 | 按章节分组，折叠子任务，显示状态、日期、优先级与标签；打开详情编辑 |
| 看板 | 按推进状态或章节查看任务 | 可按状态或清单章节分列；拖动修改该任务的状态或章节；首版不在看板拖动改变父子关系 |
| 日历 | 决定什么时候实际做 | 周视图、月视图、全天区域和未安排区；拖动修改计划日期/时间，调整时间块修改预计时长；截止日期以独立标记显示 |
| 记录 | 回顾做过什么和留下什么 | 按日期聚合完成/重开历史与手写进展；支持按目标/任务筛选、打开成果资料 |

首版不绘制任务依赖网络和甘特条。任务可标记「阻塞」并填写原因，但阻塞原因不构成自动调度依赖。

### 3.1 导航与详情

- 沿用「应用 → To Doo」入口，可返回应用主页；保留 DooKnow 的账号和设置入口。
- To Doo 内提供常用入口、清单/目标列表和当前模式。任务详情包含基本信息、安排、资料、完成标准和历史。
- 支持目标、任务和日历日期的地址定位、刷新、前进后退。同服务内部链接使用任务稳定 ID，不把本机绝对路径写进链接。
- 桌面可使用列表与详情并列；手机通过单页详情/抽屉完成同样操作，不要求同时显示多栏。
- 任务表单使用「创建/保存」明确提交；勾选、状态切换与日历拖动是直接提交的单次操作。离开未保存表单保留提醒。失败后保留输入，拖动失败回到已保存位置。
- 「保存成功」表示对应便携文件已经持久化；本机待写或结果待核对不能显示成已完成保存。Git 提交状态单独呈现。

### 3.2 状态与进度

任务状态为 `todo`（待处理）、`doing`（进行中）、`blocked`（阻塞）、`done`（已完成）、`cancelled`（已放弃）。放弃与删除是不同操作，放弃的任务仍可查询并恢复进行。

父子任务分别保存状态，不级联修改。父项有未完成子任务时不能标记完成；子项全部完成后显示「可完成父任务」，由用户单独勾选。重新打开子任务不会偷偷重写父文件，而是显示父项与子项状态不一致的提示。

目标进度按未删除、未放弃的叶子任务计算：已完成叶子数 / 有效叶子总数。父项不重复计数，空清单显示「尚未添加任务」。重复任务显示当前一期状态，历史完成次数单独展示；该比例是行动进度，不是能力评估。

在默认列表中按清单章节及层级显示；看板中的子任务卡片保留父项路径。移动到新章节不改变父子关系，允许子任务与父项分属不同章节。普通删除前若仍有子任务，应先处理子任务；首版不隐式级联删除。跨清单移动只支持没有子任务的任务，移动后成为目标清单的顶层任务。

### 3.3 日期入口的判定

「今天」包括今天计划做或今天截止的未完成任务，同一任务只列一次，逾期项另列提示区。「未来七天」包括今天及之后六个日历日内有计划或截止的未完成任务。「未安排」指没有计划日期，仍可有截止日期；「逾期」仅由截止时间决定，与计划推迟无关。已完成、已放弃、已删除任务不进入这些默认行动入口。

日期筛选默认使用 To Doo 设置中的时区：有具体时间的安排转换为该时区再分日，全天日期保留原日历日期。日历以计划时间块为主体，只有截止的任务显示截止标记，不能据此视为已经安排工作时间。已完成入口按完成时间查看当前已完成任务，完整的重复完成与重开过程在记录模式查看。

## 4. 关键使用流程

### 4.1 从资料形成行动

在已保存的普通笔记中选中文字，点击「添加到 To Doo」，预填标题与来源，选择清单和安排后创建。若选择来自未保存的草稿，明确提示来源仍是草稿；首版要求先保存笔记，再创建可定位来源的任务。

来源保存稳定 `noteId`、选择文字、原内容 hash 与行号提示。现有正文没有永久段落 ID：内容匹配时可以定位；修改后无法可靠匹配时打开整篇笔记，并显示原引用，不跳到一个可能错误的位置。

任务也可关联多篇笔记或白板。笔记移动/改名后依靠稳定 ID 找到新位置；笔记被移入回收站或尚未同步时保留任务和关联，标记「资料暂不可用」，不级联删除任务。

### 4.2 安排与完成

「计划日期」回答准备何时做，「截止日期」回答最晚何时交付。拖动日历只改计划，不自动推迟截止；计划晚于截止时给出提示，用户可分别修改。

完成任务可直接勾选，也可填写结果、关联已有成果笔记。状态、完成时间及本次成果快照在同一个任务文件中保存，避免勾选成功却丢失完成记录。再次打开任务时追加重开记录。

进展记录是独立的可选内容，例如「练习发现重传与流控容易混淆；下次补一张对比图」。首版不自动往已有笔记写入结果；记录中的下一步若需成为任务，由用户另行创建。

### 4.3 简单重复任务

- 首版重复只支持无父项、无子任务的任务，且必须有截止日期作为周期锚点。
- 同一任务文件表示一个重复系列，只有一个当前实例。`occurrenceId` 标识当前一期，完成后将本期快照写入该文件的历史，再推进到下一期。
- 周期固定依照锚点日期；提前或迟完成不将规则改成「完成后 N 天」。完成时取晚于本期日期、且截止瞬间晚于完成时刻的下一合法周期；全天任务以当日结束为截止，因此允许推进到当天。界面显示下一日期供核对。
- 错过多个周期时不批量制造历史待办；记录跳过区间和数量。用户也可主动跳过本期。每月 31 日在短月落到月末，之后仍按原锚点 31 日计算，不漂移成每月 28 日。
- 下一期保留标题、备注和通用资料关联；清空本期成果、提醒处理状态和计划安排。截止时间、时区及提醒规则继承。达到结束日期后结束系列。
- 重复进行期间任务状态对应当前一期；推进后回到 `todo`、`completedAt: null`。若没有合法下一期，保留最后一期为 `done` 并记录系列 `endedAt`；主动结束重复则标记 `cancelled` 并记录 `endedAt`。结束的系列不再调度提醒。
- 日历只展示当前一期，不虚构未来已创建的任务。未来重复预览、单期改规则与批量编辑后续周期属于后续版本。
- 修改重复规则会生成新规则 ID，从当前实例起生效；已完成快照保留原规则。对重复任务「撤销刚才完成」必须在下一期尚未修改时原子恢复上一期；撤销追加带原事件 ID 的反向记录，不抹除历史。统计排除已撤销的完成事件。不满足撤销条件时只能查看历史，不自动覆盖下一期变化。

## 5. 提醒设计与送达范围

### 5.1 首版渠道

服务端独立于浏览器页面扫描到期规则，将待处理提醒保存在本机 SQLite 的运行表。页面在线时实时或轮询更新站内提醒中心；重启后重建未完成调度，重新访问时可看到错过提醒。

浏览器系统通知可作为页面在线时的可选增强：需要用户主动开启并获得浏览器许可；失败时仍保留站内提醒。首版不安装 Service Worker/Web Push，不承诺关闭网页、手机锁屏或设备离线后的即时外部通知。设置页必须清楚显示实际支持范围，不能只显示笼统的「提醒已开启」。

### 5.2 时间与处理

- 每任务最多 3 条提醒规则，首版提供到时、提前 15/30/60 分钟和提前一天；独立自定义多个任意时间点后续扩展。
- 定时截止以指定时间为提醒基准；全天截止以该时区当日默认 09:00 为提醒基准，但逾期仍按当日结束判断。默认时间可在设置中修改，仅影响此后保存的提醒规则，不偷偷移动既有提醒。
- 提醒只作用于当前未完成、未放弃、未删除的实例；提醒条件变更后旧队列立即失效。
- 用户可以确认、忽略、稍后 10 分钟/1 小时。处理状态和稍后时间保存在对应任务文件中，换机后仍可识别已经处理的提醒。
- 提醒键由 `taskId + occurrenceId + scheduleRevision + reminderRuleId` 构成；本机唯一约束避免同一期被重复入队。投递尝试和重试日志留在本机，不当作用户历史提交 Git。
- 错过的多条提醒在站内汇总，不在重新登录或重启时逐条弹出系统通知。服务端停机期间不可能发送实时通知，恢复后显示错过状态。

### 5.3 换机与恢复

首次在新实例导入 To Doo 数据、恢复备份或识别为新提醒主机时，站内内容照常恢复，外发系统通知默认关闭。由使用者在通知设置中指定接管提醒，并停用旧实例的通知。提醒主机标识、通知订阅和通知启用开关属于本机设置，不放进 Git。

首版按一个通知主机设计；Git 同步不提供跨主机锁，不能保证两个独立服务同时通知时绝不重复。

## 6. `_data` 数据结构

以下路径相对于知识库根目录，不是 DooKnow 源码目录。沿用根级 `_data/manifest.json`，不改动既有 `library/`、`apps/blog/` 和 `plugins/`。

```text
knowledge/
├── 原有笔记和附件目录/
└── _data/
    ├── manifest.json
    ├── library/state.json
    └── apps/
        └── to-doo/
            ├── manifest.json
            ├── settings.json
            ├── lists/
            │   └── <list-id>.json
            ├── tasks/
            │   └── <task-id>.json
            └── records/
                └── <record-id>.json
```

任务专属附件上传不在首版范围，暂不创建 `assets/`。后续若支持，以内容哈希独立保存；已有知识库资料继续通过笔记 ID 引用，避免复制原文或移动原有附件。

### 6.1 统一格式与身份

所有 JSON 使用 UTF-8、固定字段顺序、两空格缩进及文件末尾换行，便于 Git 查看差异。版本封套沿用平台惯例：

```json
{
  "format": 1,
  "revision": "<本次保存的 UUID>",
  "data": {
    "id": "<稳定实体 UUID>"
  }
}
```

`format` 是格式版本，`revision` 是每次持久化变化后更新的随机版本标识。实体 ID 在改名、排序和迁移后保持不变；文件名使用 ID，不使用标题、日期或本机路径。相同 ID 出现多个文件、文件名与内容 ID 不同、未知格式或无效字段时报告数据错误，保留原文件，不自动修复后覆盖。

清单、任务和记录均包含 `creation`（原创建请求 ID 与请求体指纹）、`createdAt`、`updatedAt` 和可空 `deletedAt`。设置与清单等单例/实体仍使用统一封套；单例的 ID 使用固定值，不随每次启动生成。

To Doo 的 `manifest.json` 采用同样封套，包含 `appId: "to-doo"`、`schemaVersion: 1`、`appInstanceId`（知识库内该应用数据集的稳定 ID）和所需最低应用数据能力版本。它不保存全部任务的频繁变化总表，也不决定本机是否启用通知。

### 6.2 实体内容

| 文件 | 权威内容 | 关键约束 |
| --- | --- | --- |
| `settings.json` | 默认时区、每周起始日、默认模式、全天提醒默认时间、默认预计时长 | 时区默认为知识库推荐值，可覆盖；无令牌、本机路径和通知启用状态 |
| `lists/<id>.json` | 名称、`kind: list/goal`、说明、排序、章节数组、目标日期、目标完成标准、关联资料、首选模式、看板分组方式、归档/删除时间 | 章节有稳定 ID；目标日期是日期值，不自动创建任务安排 |
| `tasks/<id>.json` | 标题、备注、状态、优先级、标签、清单/章节/父项、排序、计划、截止、重复、提醒规则、提醒处理状态、来源、成果、完成/重开历史、删除时间 | 一个文件保存一个任务/重复系列，状态和完成历史一次写入 |
| `records/<id>.json` | 进展文本、所关联清单/任务/重复实例、记录时间、可选投入分钟数、相关资料、删除时间 | 手工记录独立保存；其删除或缺失不改变任务完成状态 |

任务允许 `listId: null`，表示收集箱；此时不得有父项或章节。有父项时必须与父项属于同一清单。章节不存在时显示「未分组/分组暂不可用」，不抹除原章节 ID。目标或任务暂未同步时，进展记录保留原关联，显示暂不可用。

正文内容长度上限建议：任务标题 256 字符、备注与进展正文各 64 KiB；每项最多 20 个标签、20 个资料引用；任务总文件含历史最多 4 MiB。首版工程基准为 10,000 项任务，列表分页、日历按可见区间查询；超过限制明确提示并保留原数据，不静默截断历史。

补充字段定义：

- `priority` 为 `none/low/normal/high`；`estimateMinutes` 是独立、可空的预计投入，因此未安排任务也能估时。无安排时 `plan`、无截止时 `due` 均为 `null`。计划 `durationMinutes` 是本次日历预留时长，与任务估时分别保存；拖动创建时间块时优先采用估时，否则使用设置中的默认时长。有计划日期但无时间表示全天安排，不绘制小时块；不支持只有时间没有日期。
- `repeat` 非空时包含规则 ID、`frequency: daily/weekly/monthly`、正整数 `interval`、`anchorDate`、适用的星期数组或每月日期、可空 `untilDate/endedAt`。规则与下一实例的计算以其截止时区为准。
- `history` 按顺序记录完成、重开、跳过和结束系列，条目有独立 ID、请求 ID、时间、实例 ID及当时标题、计划、截止、结果、成果引用快照。重试同一请求不追加第二条历史。未到需要记录的行为不写每次键盘输入或计时器 tick。
- `reminderReceipts` 保存本期提醒键、`acknowledged/dismissed/snoozed`、处理时间及可空 `snoozedUntil`。推进重复实例时收进该期历史，当前期重新开始。具体浏览器投递记录不写在此处。
- `scheduleRevision` 只在截止、重复或提醒规则实际变化时更新；普通标题修改不触发旧提醒重发。无截止时不能设置依赖截止的提醒。
- `createdAt/updatedAt/completedAt/deletedAt` 使用 UTC 时间戳。计划、截止和重复使用本地日期/时间加 IANA 时区，全天日期不会因设备切换时区变成另一日。显示默认保留任务时区，并可标注当前设备的对应时间。
- 夏令时不存在的本地时间提示用户选择有效时间，不静默改时；重复计算遇到该情况顺延到缺口后的首个有效时间，回拨歧义固定取较早的瞬间。计算必须使用同一套时区规则并覆盖测试，不自行用固定 UTC 偏移代替。

### 6.4 删除、恢复与引用

删除写入 `deletedAt` 并保留原文件，便携回收站据此查询；恢复清空该值并更新版本。首版不在界面永久清除 To Doo 数据，避免离线旧副本带回已删除记录。将来若增加清理，须另定墓碑保留和多副本处理规则。

父任务有子任务时禁止直接删除；清单有未删除任务时可归档但禁止删除。归档保留任务及提醒，若要暂停提醒需单独取消任务提醒；界面在归档前展示这一行为。只有空清单能进入回收站。被引用资料缺失只影响关联显示，不破坏任务和记录。

## 7. 保存、SQLite 与 Git 一致性

### 7.1 权威来源

便携文件是长期内容的权威记录。SQLite 中任务、视图查询、关联和进度是可重建投影；调度、请求回执、未完成写入和锁属于本机运行状态。只有确认不存在待写操作后才允许丢弃投影并重建，不能把运行数据库当作随时可删除的缓存。

写接口使用实体 `expectedRevision` 与 `requestId`：同一版本修改失败时返回冲突并保留表单；相同请求重试返回同一结果，相同 ID 携带不同请求体拒绝执行。创建任务/记录的实体 ID 和创建请求指纹进入对应文件，导入新库后也能识别创建重试；完成等有历史的动作在历史中保留请求 ID。其它修改请求的回执至少留存在本机，以版本核对避免未知结果被重复应用。

写入使用暂存文件、原子替换、磁盘同步和预期 digest 检查；SQLite 待写记录保存期望基线及目标内容，中断后对账恢复。文件已经替换但响应丢失时，重试不能重复创建或再次推进重复周期。磁盘空间不足、文件权限和同步冲突均需要可见错误。

### 7.2 新增文件集合能力

当前 `createKnowledgeDataDomain` 处理的是单路径、单文件、整域导入/导出；不能把一任务一文件描述成已经具备的能力。To Doo 实现需要补充通用的文件集合适配器：

- 为每个实体维护基线 digest、版本、dirty 和 pending，对发生变化的实体登记待写。
- 集合级使用固定数量的登记机制；不得为每个任务创建一组 SQLite 触发器，也不得在每次请求里完整刷新所有任务文件。
- 支持实体文件的新增发现、有界扫描、增量刷新、删除标记、已知文件意外消失检测及根目录切换后的注销。
- 复用现有 `_data` 安全路径检查、禁止软链接/共享硬链接、原子写入与恢复约定，不复制一套不兼容的实现。
- 导入前先恢复笔记身份映射，再校验 To Doo 文件与引用；任务树不能成环，不存在父项或清单时保留原 ID并标为关联不完整，不把实体抛弃或自动移入收集箱。
- 缺少资料属于引用警告，不阻断普通任务读写；缺少父项/清单的任务显示在「关联待恢复」区域，只允许查看，不允许在关系不完整时移动或删除。其它完整任务照常使用。格式损坏、循环关系或写入冲突才触发下面的应用级只读保护。
- 一轮导入先完成校验，再在 SQLite 事务中切换投影。发现冲突或损坏时 To Doo 进入只读待核对状态；可以显示明确标为旧快照的上次可用内容，不能冒充最新状态。

任务 `listId/parentId/sectionId/orderKey` 均放在任务自身，列表和章节不另存反向任务 ID 数组，减少多文件改写。普通创建、修改、完成、移组、叶子任务跨清单移动均只修改一个实体文件。

首版不提供跨多个实体的原子批量修改、级联删除和「同时新建笔记并完成任务」。成果先保存为普通笔记，再关联到任务；两步失败时留下可见的已保存笔记，不假报整体回滚。

### 7.3 Git、外部修改与恢复

- `_data/apps/to-doo/` 纳入知识库 Git；应用不自动创建提交或推送。备注、记录和规则以可读文本产生差异，不加入 SQLite/WAL、令牌、日志或设备订阅。
- 接入现有工作区写入闸门：提交、备份前排空可确认的待写；拉取前阻止未保存表单和未解决冲突；拉取后刷新投影和调度，再接受新修改。
- 外部变化与本机待写同时存在时，保留双方并报告冲突；不得按时间戳选一个版本直接覆盖。不同任务拆文件减少冲突范围，不代表同一任务可自动合并。
- 首版通过已有 Git 差异/同步冲突入口核对数据，不提供 To Doo 专用三方合并器。冲突解决后重新校验整个受影响关联部分，再恢复写入。
- 已知实体文件被直接删除不等同于应用内删除：提示数据缺失，不能从旧投影自动补回，也不能悄悄清空。新机器需从完整 Git 提交或一致性备份导入；无全量实体清单时，不能仅凭目录扫描证明任意半拷贝已经完整。
- 全库备份必须覆盖便携文件和一致的本机数据库；有待核对写入时明确保留恢复材料。任务回收站与 Git 历史分别存在，普通笔记导出继续排除 `_data`，整库迁移包含它。
- 笔记 ID/相对路径映射先于任务恢复；新实例可以使用不同的本机主人 ID，任务内容不绑定旧认证 ID。恢复不带回旧登录会话、通知权限或秘密配置。

## 8. 应用接入与权限

沿用现有 Vue 3、Ant Design Vue、Fastify、TypeScript 和 SQLite 技术栈。保留博客原生应用模式，不为本次工作先建设应用市场或另起独立常驻服务。

建议的代码职责，不是本次已创建的文件：

| 范围 | 职责 |
| --- | --- |
| `shared/to-doo-contracts.ts` | 版本化数据类型、输入输出与校验约束 |
| `packages/core/to-doo/` | 任务、清单、重复、记录、便携投影和提醒业务 |
| `packages/core/knowledge-data.ts` 及集合适配层 | 可复用的文件集合读写和恢复 |
| `apps/server/to-doo/` | 主人 Web API、提醒生命周期及状态接口 |
| `apps/web/components/ToDooWorkspace.vue` 与工作台状态模块 | 子应用各模式、详情与保存状态 |
| 既有导航、平台 runtime、工作区 gate、Git/备份集成 | 入口、前进后退、生命周期、同步与恢复 |

Web API 统一置于 `/api/to-doo/`，覆盖 dashboard、lists、tasks、records、settings、reminders 和应用健康状态。可变实体接口使用 `requestId/expectedRevision`；列表分页、日期区间和结果数量有界。任务、提醒和进展必须经同一业务层修改，不能绕过便携文件直接操作 SQLite。

所有首版接口只对当前主人会话开放，继承现有登录、维护模式、Origin 与 CSRF 保护；To Doo 不产生公开页面。`_data` 不通过普通笔记、附件、分享或搜索 API 直接公开。用户填写的备注/记录按现有安全 Markdown 方式展示。

首版不扩展 MCP 权限。后续增加任务读写时，单独设计任务能力和授权；现有 `knowledge:read/write` 不能默认获得整个 `_data` 或 To Doo 数据。资料链接的访问仍服从原笔记授权，不因为任务引用而扩大范围。

## 10. 后续版本与实施裁量

后续优先次序建议：关闭网页后的 Web Push 与设备管理 → 任务 MCP 及基于资料的计划建议 → 未来重复预览与时间线 → 专注/习惯/四象限 → 日历订阅与外部导入。若用户的首要目标变成全面替代手机提醒，需要先扩大通知范围并更新本设计。

实施者可以自行决定组件拆分、SQL 索引、分页游标、轮询/事件通知、集合扫描调度、拖拽库与时区计算库的选型，以及排序键算法；须复用项目依赖与主题并满足本文件约束。排序键相同须用稳定 ID 决定顺序，重排只能更新实际变动实体。

不得自行扩大首版为多用户、实时跨主机同步、自动 Git 推送、自动安装插件、公开任务或 AI 自动执行。设计确认后的下一步是实施计划；本次交付止于设计文档和审阅。
