# MCP 分域权限与知识库自主整理设计

日期：2026-10-29（Asia/Shanghai）

状态：设计稿，待用户审阅；本文件不表示相关能力已经实现或部署。

## 1. 已确认的目标

用户希望 AI 通过 MCP 实时了解知识库结构，自行选择保存位置，并创建目录、创建及修改笔记、移动和重命名已有笔记及目录，维护整个知识库结构。选择“全库自主整理”后，日常操作不逐次要求用户确认。

权限在 MCP 插件设置和客户端授权中一次设定。权限管理按知识库、博客、待办等业务域分层，业务域内部再区分操作能力和资源范围，避免以后增加博客、待办时沿用一个笼统的“可写”开关。

本期交付范围：通用分域权限基础、现有知识库与博客接入、知识库结构发现和自主整理。待办只定义接入契约，不创建待办业务、工具或后台运行的模型。自主指 Agent 在一次保存或整理任务内完成工作；持续无人值守巡检需要将来另行接入调度。

以下具体接口、数值预算、迁移方式和系统目录边界是设计建议，不将其表述为用户已经逐项确认的要求。

## 2. 现状与必须解决的问题

- `plugins/mcp/manifest.json` 现有 `readOnly`、`allowedPrefixes`、`allowIndex`、`allowPublish`；`shared/authorization-scopes.ts` 当前仅列出知识库 read/write/index 和博客 publish。
- `packages/core/auth/grants.ts`、OAuth、Tunnel 和宿主 PluginServices 已有实时授权检查，但目录范围基本依赖路径前缀，`readOnly` 同时影响知识写入和博客发布。
- MCP 有 `list_notes`、搜索和笔记写入，没有目录发现、目录创建和结构整理工具，空目录不可发现。
- `packages/core/files.ts` 不仅有默认分类，还在路径校验和扫描中硬编码了顶层分类。全库整理必须使普通顶层目录能被动态发现、创建和重命名；仅扩大权限列表不足以实现。
- 现有 `packages/core/knowledge/move.ts` 保留笔记 ID、有版本及恢复证据，但跨目录正文含相对引用时拒绝移动；不能直接当作完整引用修复能力复用。
- 现有 SQLite 操作收据、workspace gate、文件写入意图、快照和 worker 可复用。磁盘多文件操作不是一笔 SQLite 原子事务，需要单独的持久化恢复协议。
- 当前工作区存在用户未提交的前端和测试变更。设计只新增本文件；实现应隔离工作，并在改动现有授权界面前保留用户工作。

## 3. 方案选择

| 方案 | 取舍 |
| --- | --- |
| AI 逐项调用基础文件工具 | 开发较少，但引用修复、批量一致性、失败恢复容易分散在不同调用中 |
| AI 判断归属，宿主执行受权限约束的整理任务 | 复用当前连接的 AI，由宿主统一处理关联文件、权限与恢复；采用此方案细化 |
| 内置模型持续整理 | 需要另配模型、费用和调度，不是本期默认使用方式 |

用户选择了在插件中分层授权并支持全库自主整理。整理任务的检查、暂存和提交属于后端内部过程，不增加“先给用户看计划再确认”的日常步骤。

## 4. 权限层级与统一判定

权限层级为：宿主与插件能力上限 → 插件分域策略 → 客户端授权 → 当前工具所需操作及受影响资源。

有效权限取各层交集。任一层拒绝即拒绝；工具可见、AI 生成了方案、拥有全库范围，均不代替具体操作授权。用户可暂停整个 MCP 连接；各域也可独立关闭。

统一权限注册表由宿主拥有，定义 domain、action、资源类型、工具依赖、界面说明及是否已经实现。插件只能请求宿主登记的权限，不能自行注册能绕过宿主检查的新权限。未知域或 action 默认拒绝。

OAuth 对外继续使用 `domain:action` scope；后端采用分域结构，避免把目录范围套到博客或待办。`offline_access` 是连接协议权限，不属于任何业务域。相同策略同时用于 OAuth 与 Tunnel。

建议规范模型：

```ts
type ResourceSet =
  | { mode: 'all' }
  | { mode: 'selected'; resources: ResourceRef[] };

type DomainGrant = {
  enabled: boolean;
  actions: string[]; // 必须来自该域的宿主注册表
  resources: ResourceSet;
};

type PermissionPolicy = {
  version: 2;
  domains: Record<string, DomainGrant>;
};
```

`ResourceRef` 使用域内稳定 ID 和已注册的资源种类；知识库是目录或笔记，博客是站点或文章，将来待办是清单或任务。资源集合同时绑定 owner 和域实例；知识库绑定 libraryId。“全部”指这个域实例的全部业务资源，绝不是主机文件系统、其他用户或其他业务域。

集合求交规则：all∩selected=selected，all∩all=all；selected 中目录包含后代，祖先与后代选区求交取后代，互不包含则为空；笔记等叶资源只匹配相同身份。返回 effective policy 时按当前资源关系计算。

一次工具调用可能有多个权限需求。注册表声明全部需求，后端逐项验证，不能只检查工具名称前缀。例如从知识笔记发布博客，需要博客发布权限和对应知识原文、附件的读取权限。

### 4.1 业务域与操作

| 域 | 本期操作能力 | 资源范围与边界 |
| --- | --- | --- |
| knowledge | read、write、organize、archive、index | 全部知识业务资源，或选定笔记/目录及后代；organize 不隐含 archive |
| blog | read、publish | 全站或选定文章；publish 包括现有显式发布与撤下，保留用户明确表达公开意图的要求 |
| todo | 本期不启用 | 预留 read、write、organize、archive 等名称，实际接入时登记清单/任务及依赖 |

知识库 write 表示创建、更新和局部修改笔记；organize 表示创建目录、移动和重命名笔记及目录。编辑模式不默认获得目录整理权。预设负责选中必要依赖，但权限引擎不把一个 action 隐式扩展为整个域的管理权。

博客将来若支持独立草稿编辑，再登记 blog:write；此时不扩大已经授出的 blog:publish 权限。博客公开发布不会因为知识库整理而自动发生。待办未实现前不在界面显示可开启选项，也不宣称工具可用。

域之间互不隐含授权：知识库全库整理不授予博客发布或待办写入；待办引用一条笔记不自动获得原文读取权。现有 publish 工具不修改原文，v2 仅依赖 knowledge:read 与 blog:publish，不再要求 knowledge:write；读取发布状态还需要 blog:read 及其返回的私有原文信息所需的 knowledge:read。发布时再次核验全部原文与附件依赖。

### 4.2 用户界面

MCP 设置按业务域呈现卡片，每个卡片有启停、能力预设、资源范围和可选的独立权限。默认无需展开高级选项。

知识库预设：只读（read）、内容编辑（read/write）、自主整理（read/write/organize）。归档和手动维护索引独立勾选。资源范围选“整个知识库”或“指定目录/笔记”。

博客提供查看、允许公开发布，资源选全站或文章；发布能力的原文读取依赖明确展示，不能偷偷选择知识库写入。后续增加草稿能力时扩展该域卡片。

用户本次目标配置为 knowledge 的 read/write/organize + all，不自动勾选归档、公开发布或其他域。插件策略是能力上限；每个已连接客户端的详情显示实际获得的各域权限和范围，允许收窄或撤销。

更改上限导致权限缩小时，下次调用立即受限；扩大上限不扩大已有客户端授权。需要扩大客户端授权时，只在设置阶段一次重新授权。日常允许的操作直接执行。

## 5. 知识库范围与目录身份

### 5.1 动态目录

默认 `00-Inbox`、`10-Projects` 等仍是新库的初始目录；普通目录名称不再是路径准入白名单。扫描器从知识根目录发现符合规则的业务目录及 Markdown/白板文件，包括空目录和新增顶层目录。

所有入口统一采用新的路径规则：网页、MCP、搜索过滤、索引、导入导出、集合监听、备份恢复和分享资源检查。不能只放宽 MCP 而让其他入口继续忽略新目录。

继续禁止路径穿越、绝对路径、软链接、共享硬链接、工具隐藏文件及业务根之外的访问；保留现有文件类型和文件名限制，包括 `AGENTS.md` 保留名。全库不等于任意文件读写。

知识根目录本身、`90-Archive` 回收运行容器、`99-System` 系统容器及内部隐藏存储位置保持系统边界；本期不移动、重命名这些容器。容器中可见的普通知识内容仍按授权读取和编辑，`90-Archive/.trash` 等内部数据不作为业务条目开放。普通分类目录（包括 `00-Inbox`）可整理；收件箱默认指针跟随目录身份，不根据旧名称擅自重建目录。

默认分类引导只在建库时运行；重命名后不得因扫描或启动重新创建旧分类。README 是普通知识笔记，允许编辑和整理；涉及系统引用时由依赖检查处理。

### 5.2 稳定身份与授权继承

新增目录身份记录，包含 directoryId、libraryId、parentId、path、active 及用于识别磁盘对象的证据。笔记继续使用已有 noteId。由宿主管理的移动保持身份，授权和操作记录不通过旧路径猜测对象。

all 自动覆盖将来新增的普通顶层目录；选定目录包含其当前后代及以后创建的后代。选区根自身由更高权限操作者移动或改名后，授权跟随同一目录 ID，而不是遗留给旧路径上新建的无关目录。目标父目录仍须在执行者权限范围内，不能借“我拥有这个目录”将它移到授权范围外。

外部磁盘修改需先核对身份：可以用本机同一对象的文件系统证据识别移动；无法证明身份时标记为新增/失效，不能仅凭路径把旧授权继承给替代物。恢复工具有独立、受控的身份恢复过程。

旧路径白名单在迁移时解析为现有对象 ID；缺失路径不直接绑定后来出现的同名无关对象，保留为不可用的旧选区并在设置中提示。不同知识库重绑定不能继承原库 all 授权。

## 6. MCP 发现与工具契约

保留现有笔记读写、搜索和索引工具。新增工具名和字段为设计建议，最终 schema 在实现时保持精简，完整工具发现 JSON-RPC 帧仍须不超过现有 64 KiB 预算。

| 工具 | 作用与主要参数 | 权限 |
| --- | --- | --- |
| get_mcp_context | 返回本人当前有效的分域能力、资源范围、限制、域实例和结构版本；不列其他客户端授权 | 有效连接；仅披露调用者自身信息 |
| list_directories | 按 parentId（根用 null）、cursor、limit 列直接子目录，含空目录和可写标记 | knowledge:read，按资源范围裁剪 |
| organize_library | requestId、libraryId、expectedStructureRevision、actions；提交有界结构整理任务 | knowledge:read/write/organize，逐资源检查 |
| list_organization_history | 按 cursor 查看本人发起的整理任务及可恢复摘要 | knowledge:read，当前资源授权 |
| undo_organization | operationId、requestId；按当时执行证据构造并执行补偿任务 | knowledge:read/write/organize，全部逆操作资源当前授权 |

`get_mcp_context` 只返回已实现且当前可用的域、能力和受限的结构提示；初始化 instructions 仍提示所有工具都须实时授权。未来域通过注册表和宿主服务贡献 context，不修改这个工具的业务分支。

`list_directories` 每次只展开一层，默认 20、最多 50 个目录，使用稳定排序、绑定范围及结构版本的分页游标。数量信息仅提供已有且可靠的元数据，未知写 null；不为列目录扫描整库正文。选区祖先只返回导航所需的容器信息，不泄漏无权访问的兄弟目录或正文，也不把导航祖先标为可整理。

整理 action 仅三类：

```ts
type OrganizationAction =
  | { type: 'create_directory'; parentId: string | null; name: string }
  | { type: 'move_note'; noteId: string; toDirectoryId: string | null;
      fileName: string; expectedModifiedAt: string; expectedContentHash: string }
  | { type: 'move_directory'; directoryId: string;
      toDirectoryId: string | null; name: string; expectedSubtreeRevision: string };
```

改名就是父目录不变的 move；同名同位置是有界幂等 no-op，不生成反复整理。新建多级目录可先创建父目录取得 ID，再创建后代或提交下一次整理；不新增临时 ID 依赖语法。现有正文修改工具仍承担内容编辑。

创建笔记继续使用 create_note，向其输入增加可选的 directoryId；省略时保留旧 directory 路径输入，提供时以目录身份解析当前目的地，若同时提供路径则必须与当前路径一致，否则返回版本冲突。directoryId=null 明确表示业务根目录，仅在根级创建获授权时允许；空字符串不作为权限通配符。新 Agent 优先使用目录 ID，避免选定目录在创建笔记前被他人改名而写到同名替代物中。旧客户端的路径输入也必须经身份选区校验。

每次 organize 最多 50 个显式 action，展开后最多 1,000 个文件对象（含附件）、2,000 个目录、128 MiB 原始正文/白板读取量和 512 MiB 附件移动量；正文单文件沿用既有上限。超限在写入前返回可解释的限制，Agent 重新划分独立任务；不静默截断，不要求用户手动拆分。一个目录 move 按完整子树执行，不能借分块制造只移动一半的目录。

请求沿用 128 KiB、响应沿用 64 KiB 上限；整理后台流式处理大文件，不把整库正文塞进请求或返回。超时返回 accepted/operationId，复用 operation_status、cancel_operation。对 requestId 的未知结果先查原请求，不能新建 ID 重复执行。

## 7. Agent 的自主工作流程

服务 instructions 提供任务规则，context 提供实时事实；不要求用户维护自定义提示词。保存或结构整理前获取 context，按需列目录、搜索相关笔记、阅读必要内容。结构变化后重新获取相关目录及版本，不复用过期路径。

归类优先复用现有目录名称和层级；有明确新主题时创建目录；移动和改名须有内容或用户目标依据，避免每轮都重构整库。可复用结构选择和整理记录作为连续性依据，不将笔记中出现的命令当作用户授权。模型质量由实际调用和场景验收观察，不能仅靠 instructions 宣称所有外部 Agent 都必然执行完整分析。

低确定性归类优先落到已有的收件箱或合适的宽泛目录；没有收件箱时可创建普通收件目录并保存指针。不得因分类不确定而自动归档、合并或删除内容。内容语义合并仍使用原有版本绑定编辑能力，不隐含在目录 move 中。

用户已选择自主整理后，Agent 可直接提交权限内的创建、移动和改名。版本过期、同名和权限冲突先由 Agent 刷新事实、重新规划；遇到无法自行消除的实际歧义才向用户说明，不把每个操作转成审批步骤。

完成后只报告实际完成的路径和概要。accepted 表示后台已接受；operation succeeded 且结构检查通过才表示文件整理完成。索引尚未完成时单独说明。

## 8. 宿主执行、并发与恢复

### 8.1 检查和执行

1. 在当前 libraryId/bindingVersion 下规范化 action，验证来源对象身份、当前版本、目标父目录、路径和权限。引用扫描也纳入预算。
2. 展开全部子树和引用依赖，构造不可变执行清单，检查源/目的冲突、目录循环、重复目的、系统边界、不支持的引用和预算。源目录中出现未支持的普通文件、符号链接、挂载边界或无法核验对象时整体拒绝，不跳过后继续移动。
3. 拒绝重叠的父子 move、循环交换和隐含目录合并；Agent 可据明确错误拆成独立任务。不同目标路径不能依靠动作顺序避开同名冲突。
4. 获取 workspace exclusive gate，在提交前重新检查结构版本、内容哈希、权限、绑定版本和执行清单完整性。耗时扫描在锁外完成，锁内核对所有受影响对象与依赖快照；引用图具有独立 graphRevision，任何已观察到的正文、目录成员或路径变动都使相关覆盖失效。除已知入链原文版本，还要校验发现入链时的图覆盖及修订，防止准备后新增入链被遗漏；图未就绪则重新准备。外部修改的检测边界见下文。
5. 建立持久化 operation、每对象 journal、必要的修改前正文和目标暂存文件；同步写盘后进入 committing。按确定顺序发布目标、改写引用、更新目录/笔记/附件路径和元数据，保留 noteId、directoryId、assetId。不能用 rm+重新导入制造新身份。
6. 完成全部对象、数据库元数据和引用验证后发布结构版本并返回 succeeded。后台索引按变更版本重建；任务结果有独立的 indexState。

任务状态复用现有 prepared/queued/running/committing/succeeded/failed/cancelled/needs_reconciliation 语义。需要扩展的整理摘要与 journal 放在独立结构中，不伪装成现有 patch 结果。异步任务由宿主 worker 持有，HTTP 断开不丢失任务。

每库单一结构提交者；普通网页编辑、分享写入、MCP、Git、导入导出、备份及索引观察都遵守 gate。提交中阻止正文及树读取观察混合状态，相关 API 返回短暂可重试的维护状态；已有搜索快照在结构版本变化后过期。外部绕过应用直接修改磁盘仍可能发生，使用对象证据和哈希检测，不把 gate 描述为能锁住所有外部进程。

### 8.2 崩溃与授权撤销

文件系统与 SQLite 不承诺多文件原子性。开始变更前落盘恢复清单；重启后优先恢复未完成提交，再开放相关读写。journal 逐对象记录意图、暂存、发布和元数据阶段，依证据续做或补偿；证据冲突进入 needs_reconciliation，保留原件与暂存，禁止擅自覆盖。

队列开始和每次进入提交前重新取有效权限。撤权时取消未提交任务；已经 committing 的任务只允许受信任宿主恢复器完成已冻结清单的一致性收尾或补偿，不允许 Agent 借旧授权添加动作。撤权后不向客户端返回其已无权读取的路径、正文或详细历史；宿主维护界面可查看恢复状态。

cancel_operation 在提交前取消并清理暂存；进入 committing 后仅返回当前状态，不能声称已经撤销。磁盘满、进程退出和恢复期间错误都要保留可判定证据。

### 8.3 撤销

undo 是新的有收据的补偿任务，绑定原任务和当前授权；执行前检查所有受影响对象仍是原任务产出的版本，且旧路径可用。任意笔记随后被编辑、目录新增子项、授权变化或原路径被占用时，默认整体返回 UNDO_CONFLICT，不覆盖后续工作，也不半撤销后宣称成功。

恢复器用于完成中断的一致性操作，不能被撤销 API 当作绕过当前权限的途径。恢复与撤销记录不同状态和原因。

## 9. 引用、附件、分享和索引

移动和改名不仅处理被移动笔记的正文，还处理其他笔记指向它的入链。宿主维护带 sourceHash 的引用图，覆盖现有 Markdown 解析器支持的链接、图片、引用式链接、白板引用及附件。首次整理前须完成可验证的引用图准备；过期部分重新扫描。准备状态返回 operationId，不要求用户手动刷新索引。

路径变化计算旧路径到新路径映射。引用改写采用语法位置和字节区间，保留标题、代码块、格式、URL 编码、query 和 fragment；不做全文字符串替换。普通 #anchor、外部 URL、稳定 note/asset ID 引用不随路径变化改写。无法提供可靠源区间或超出支持语法时拒绝受影响任务，不能带着断链风险宣布成功。

移动单笔记时附件默认留在原目录，通过相对路径重算保持引用；不因一篇笔记移动而搬走其他笔记共用附件。移动目录时一起移动其中受管理的 assets，并更新附件表路径和外部入链。白板 JSON 使用明确的语法适配器；内嵌图像和 ID 引用保持稳定，路径型 link 按其真实语义处理。

引用更新涉及的每份正文都须具备当前读写权限。宿主内部可做依赖完整性检查，但不自动改写授权范围外正文；存在此类依赖时在任何写入前拒绝，并且错误不泄漏受限对象路径或数量。全库自主整理覆盖普通知识内容，所以正常全库任务无需用户另行授权引用修复。

笔记 URL 和收藏继续基于稳定 noteId；分享 token 和资源权限重新核验，不能因移动扩大原分享资源集。公开博客仍是已有的独立快照，知识库移动不会自动更新、撤下或重新发布博客。若将来维护博客链接确需改写公开内容，必须通过 blog 域的独立授权与发布流程。

变更后更新 document_state、路径、集合来源和受影响正文版本，排队处理全文/向量索引；旧位置不能继续作为有效检索结果。正文未变而路径改变时，也需刷新参与索引或 embedding 输入的路径元数据。索引、引用图及整理 journal 的有效版本不能互相冒用。

## 10. 数据记录与保留

新增数据放在既有服务持久数据区与 SQLite，不在知识库中散落 AI 提示词文件，不另建常驻服务目录。

- 版本化 permission policy、分域资源集合、客户端 grant 及其版本。
- libraryId、目录身份与当前路径、structureRevision；子树修订包含空目录和对象替换。
- 原文版本绑定的引用记录及覆盖/新鲜度信息。
- organization operation、对象 journal、必要的修改前正文和完成摘要；记录原/目标路径、受影响身份、调用者、requestId、理由、时间和结果。

正常调用日志只记录安全概要，不写正文或凭据。修改前正文和详细恢复清单按原文同等级权限保护，权限缩减后不得通过历史接口泄漏。

已成功任务的撤销材料默认保留 30 天；未终结或 needs_reconciliation 的材料不按期限自动清理。保留期限在维护设置高级项配置，不增加日常操作。过期历史仍可显示安全摘要及 undoAvailable=false；清理只影响撤销材料，不删除知识正文。存储不足时在写入前返回可处理错误，不静默清除未到期的恢复材料。备份包含策略、目录身份及恢复记录，索引可重建；恢复时先解决未完成 journal 再开放写入。

## 11. 兼容与升级

本设计需要宿主 API 增量版本，建议 HOST_PLUGIN_API 1.2.0，MCP 插件声明 ^1.2.0。已有 KnowledgePort 方法保持兼容，通过可选的 knowledgeOrganization 服务和仅返回本人权限的 permissions.context 服务新增能力；旧插件无需实现新服务。不得给 MCP 原始文件系统或任意命令执行权限。

宿主能力列表、scope 注册表、OAuth consent、Tunnel 身份、PluginServices、旧 Agent assertion 路径均接入同一个规范化权限引擎；没有显式资源模式的旧调用者仍按原目录范围检查，不能因宿主支持 all 而获得全库访问。新插件装在旧宿主上须清晰拒绝，不能忽略新权限后降级成无限制写入。

旧配置按 v1 语义确定性解释：readOnly 控制既有知识写入，allowedPrefixes 形成旧选区，allowIndex 控制索引，allowPublish 结合旧只读开关控制既有博客发布。旧 knowledge:write 目前含归档，因此仅在带持久化 v1 授权版本标记的旧连接中保留这个既有含义；不新增 organize、不变成 all，也不新增未来域。新建或重新授权的 v2 连接中，archive 必须显式授予，不能再把 write 当 archive 的别名。旧博客 publish 的既有查看能力可在 v1 适配器中保留，但不赋予未来草稿编辑能力。

v1 适配器同时考虑令牌签名 scope、原 grant、插件上限和当前用户；版本标记由宿主控制，客户端不能通过输入声明自己是旧授权。v2 编辑后生成新的 grant version 并使旧令牌失效，不允许在新策略下继续走 v1 别名。

把权限升级到全库自主整理属于一次明确的设置与客户端授权变更；后续日常创建、移动和改名不再询问。旧数据迁移默认只增加元数据、不整理实际目录、不自动启用插件或后台任务。先完成迁移与备份/恢复兼容验证，再启用结构写入能力。

## 12. 验收场景

1. 只读连接能发现授权范围内的新空目录，但不能创建、编辑或移动；编辑连接可以写笔记，不能改目录结构。
2. 开启全库自主整理后，AI 在一次任务中发现新空目录、创建多级目录和笔记，并移动/重命名已有笔记与普通顶层目录，无逐次确认。
3. 启用后在界面或磁盘新增普通顶层目录，Agent 下一次查询即可发现；扫描、搜索、集合与导出不遗漏该目录。
4. 指定目录授权覆盖新后代；授权根改名后跟随目录 ID，不误授给旧路径上新建的其他目录。父子选区求交、缺失旧路径和不同 libraryId 均有明确结果。
5. 知识库自主整理不能修改博客或待办；博客权限不隐含知识库写入；未实现待办权限不可启用，新增域不扩大旧 grant。
6. 相对链接、入链、图片、引用式链接、编码路径、锚点、共享附件、白板和目录外引用在移动/改名后仍指向原对象；不支持的依赖在写入前拒绝。
7. 缺少外部入链正文写权限时完整拒绝且不泄漏范围外细节；all 不允许触达隐藏存储、任意主机文件或其他知识库。
8. 与网页编辑、分享写入、Git 同步及磁盘外部修改并发时，检测版本冲突，不覆盖新内容；依旧 requestId 重试只返回一次任务结果。
9. 在 journal 各提交边界注入退出、磁盘满和数据库错误，重启后恢复一致状态或保留明确冲突，不丢正文、附件和稳定身份。
10. 队列撤权和提交中撤权有上述不同结果；旧凭据、旧 v1 标记和过期游标不能扩权。
11. 撤销未被后续修改的任务可恢复原结构和引用；编辑后撤销返回冲突。30 天清理不删除原文或未完成任务材料。
12. OAuth、Tunnel、SDK tools/call 和网页权限显示一致，完整工具列表与成功/错误响应符合现有大小预算；实际打包宿主验证新旧版本兼容。

本轮只验证设计与源码对应关系。实现阶段在临时知识库完成以上功能与故障测试，不对真实知识库运行整理验收。

## 13. 实现阶段可自行决定的细节

实现者可选择表名、迁移编号、worker 的内部模块拆分、引用解析库、页内排序实现和界面卡片样式；必须满足上述权限、引用覆盖、持久化恢复与兼容契约。本文预算是初始默认值，若性能测量要求调整，须保留有界和写入前完整拒绝的语义并记录依据。

尚不引入：无人值守模型调度、自动公开发布、待办业务实现、隐含目录合并、永久删除或任意格式文件管理。
