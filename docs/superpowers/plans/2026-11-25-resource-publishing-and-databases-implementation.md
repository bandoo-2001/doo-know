# DooKnow「资源发布」与「数据库」实施计划及验收清单

**交付阶段**　开发交接，2026 年 11 月 25 日。本轮交付本文档。文末清单用于未来实现的验收。

**产品目标**　用户能只发布目录、只使用数据库，也能让一个网站通过授权读写业务库。业务库属于知识库，从「数据库 → 新建业务库」即可开始。设备借用、活动报名、学习记录是验证同一套能力的三个例子。[总体计划书](2026-11-25-resource-publishing-and-databases.md)

## 1. 从哪里开始

**先定入口与身份，再分两条线开发。** M1 交付两个可独立进入的工作区和共享接口约定。之后 M2 做网站发布，M3 做独立业务库，两者可以并行。M4 在 M3 上完成联表与跨表事务。M5 汇合两条线，完成网站绑定、API 与 MCP 授权、示例站及恢复演练。

## 2. 产品决定、首版建议与待确认项

| 类别 | 交给开发团队的结论 |
| --- | --- |
| 已确定 | 两个应用各有入口。网站实时读取源目录，业务库可独立创建。网站可以绑定已有库或一键创建专库，首版每个站点同时最多绑定一个库。解除绑定撤销该站点访问，库的生命周期由「数据库」管理。 |
| 已确定 | 每个业务库拥有独立便携目录、SQLite 查询库和权限。联表与事务在同一个库内执行。个人网站支持按站点邀请成员。公开文件、检索文件、读记录和写记录分别授权。 |
| 首版技术建议 | 用稳定 ID 标识库、表和字段，显示名可改。`_doo-data/apps/databases/<dbId>/` 保存便携文件，`<dataRoot>/databases/<libraryId>/<dbId>.sqlite` 保存本机投影。每个 SQLite 内按表 ID 共用记录表，对实际筛选和排序字段建立索引。 |
| 首版技术建议 | 用结构化 JSON 表达查询、前置条件和变更。一般字段支持文本、数值、布尔、日期时间、枚举、JSON 及同库引用。网站权限限定到库、表、动作及记录范围。服务端维护成员归属、时间、版本等受保护字段。 |

| 仍需确认 | 采用的工作假设 | 何时决定 |
| --- | --- | --- |
| 一个已绑定库是否接受第二个网站 | 数据模型支持逐站授权，默认展示“创建专用库”。首版如开放第二站绑定，则分别授权和撤销，两站使用不同会话。确认前用未绑定的已有库验证绑定流程。 | M5 绑定页定稿前。M2、M3 可先推进。 |
| 不可逆清理的保留期限 | 先提供停用、解除绑定和归档。单独设计库删除时的依赖预览、备份与保留期限，由站主在数据库应用发起。 | 接入库删除前。 |
| 实际数据量及外部域名 | 用临时知识库、回环端口、两个模拟站点域和一万条合成记录验证。查询上限及性能目标按典型样本校准，真实域名和证书在部署阶段配置。 | 查询预算在 M4 定稿，公网配置在后续部署时决定。 |

## 3. 五个里程碑

### M1　双应用入口与独立导航

**用户操作与依赖。** 用户能从应用页分别到达「资源发布 → 发布目录」和「数据库 → 新建业务库」。先约定 `siteId`、`dbId`、`tableId`、绑定状态及错误类型，供 M2、M3 并行对接。

1. 扩展 `workspaceApps`、`WorkspaceAppId`、`WorkspaceRoute` 的读写和 [Workspace](../../../apps/web/components/Workspace.vue) 的导航与应用宿主分支。建议应用标识为 `publishing`、`databases`，数据库详情 URL 只携带库、表及子页信息。
2. 「资源发布」有网站列表、目录预览和绑定入口。「数据库」有库列表、独立建库、表与记录、查询、事务回执。空网站列表与空库列表各有自己的创建操作。库详情显示已绑定站点和当前库。切库前沿用现有离页处理保护未保存表单，切换后重置表选择、未运行的查询和回执视图。
3. 在 `shared/` 增加发布与数据库两组接口类型。M1 的组件验收可注入测试适配器，正式入口在 M2、M3 接真实服务。M5 接通绑定按钮。把旧原型中固定的设备、报名场景移到示例夹具。

**验证与完成标准。** 使用桌面、手机浏览器检查空状态、深链刷新、后退、固定到导航以及双入口独立性。直接打开一个无绑定库，面包屑为「数据库 › 设备库」，选表器不出现其他库的表。旧应用路由回归可沿用[导航测试](../../../tests/web-navigation.test.ts)和[快捷入口测试](../../../tests/app-shortcuts.test.ts)。对应 A1、A4。

### M2　目录实时发布

**用户操作与依赖。** 从知识库任选一个普通子目录，预览、启用、修改或停用映射。依赖 M1 的站点契约，可与 M3 并行。

1. 新增发布领域服务和主人管理路由，建议位于 `packages/core/publishing/`、`apps/server/publishing/`。选择器从当前知识库根开始，可选只有 HTML 或附件的目录。建议将站点 ID、相对目录和唯一路径名存入 `_doo-data/apps/publishing/sites/<siteId>.json`。每次启用时在本机登记知识库身份、绑定代次和实际目录身份，换绑知识库或源目录自身被替换后转入待核对状态。
2. 为资源域配置独立的只读监听器，绑定回环地址，提供 `GET` 和 `HEAD`。开发启动、原生启动与停止共用该监听器的生命周期。通过实例配置设置资源来源和端口，附独立反代示例。普通静态站使用 `pub.example.com/<slug>/`，管理端路由与会话只进入管理来源。[开发入口](../../../scripts/dev.ts) · [原生入口](../../../scripts/manage.ts) · [实例配置](../../../apps/server/platform/config.ts) · [代理示例](../../../deploy/Caddyfile)
3. 预览、HTTP 和后续索引共用同一套文件解析。复用 `validateRelative` 的路径规则和 `openDirectory` 的描述符遍历方式，核对根目录身份及已打开文件的类型、链接数，再从该描述符读取。知识库根、隐藏路径、内部数据目录 `_doo-data`、链接和特殊文件均不可发布。`/manual` 保留查询参数跳转到 `/manual/`，目录有 `index.html` 时返回首页，其他普通文件按 MIME 类型发送，缺失文件返回 404。未版本化 URL 每次重新校验，停用检查先于缓存命中。[路径规则](../../../packages/core/files.ts) · [目录遍历](../../../apps/server/platform/storage.ts)
4. 保存、外部编辑、Git 拉取和恢复源文件后，下一次请求读取当前文件。变更可移植站点定义时重新核对实际目录。启用状态和本机来源配置归本实例管理。

**验证与完成标准。** 启动隔离的管理端与资源端，用真实浏览器加载相对脚本和图片、直开 PDF，修改同名源文件后刷新。禁用缓存与正常缓存各验证一次。检查目录边界、站点停用、知识库换绑及旧 URL。资源域访问管理接口返回不可用。对应 A2、A3。

### M3　独立业务库与可重建存储

**用户操作与依赖。** 没有网站也可以建库、建表、录入、查看、修改和删除获准操作的记录。依赖 M1 的库与表契约，与 M2 独立。

1. 新增 `packages/core/databases/` 领域、主人 API 和独立库列表。领域入口从第一版起接收调用主体、知识库及业务库范围，M3 先接主人会话，并用受限身份夹具测试。M5 再接网站、API 客户端和 MCP。创建库时分配稳定库 ID，原子建立 `manifest.json` 与初始结构，同一创建请求重试取得同一库 ID。每库单独打开 SQLite，核对库和知识库身份，换绑或恢复时关闭旧连接。[运行时装配](../../../apps/server/platform/runtime.ts) · [知识库身份](../../../packages/core/auth/permissions.ts)
2. 每张逻辑表的 `tables/<tableId>/schema.json` 保存字段标识、类型、约束、关联和结构版本。记录文件为 `tables/<tableId>/records/<recordId>.json`。显示名修改保留字段 ID。字段改类型先用现有记录校验，再按版本迁移。新增要求记录尚不存在，更新与删除提交预期版本，删除有引用的目标默认返回冲突。新库默认仅主人管理，按库授予表、动作和记录范围，实际外部授权在宿主私有存储登记。前端提供字段编辑、关联目标、记录列表和详情。
3. 从第一条记录就复用 `writeKnowledgeDataFile` 的可靠落盘方式，参考 To Doo 的请求回执与回放顺序。先进入宿主工作区写门，与 Git、备份的独占操作互斥。再通过每库跨进程写锁串行化读版本、校验和提交，正常更新在该库 SQLite 连接上使用 `BEGIN IMMEDIATE`。重放及切换重建副本也取得同一库锁。每笔事务把调用主体标识、请求指纹、预期版本、全部结果记录或删除标记写入 `transactions/<txId>.json`，由原子改名及目录落盘形成提交点。SQLite 同一事务更新记录、库版本和已应用回执，再写出当前记录文件。中断后先重放和对账，再开放该库读写。[便携文件写入](../../../packages/core/knowledge-data.ts) · [事务先例](../../../packages/core/to-doo/store.ts)
4. 从完整便携数据向空 SQLite 重建，核对结构版本、事务前驱、记录摘要和回执后切换读视图。外部手改或 Git 导入先完整验证。缺失前序、文件损坏或同版本分叉时，报告涉及的库和记录，保留原文件及上个已验证视图供只读核对。首次重建遇到此类冲突时，隔离该库，其他库继续服务。扩展 `workspaceExclusive` 的待写检查，覆盖新库的备份、Git 拉取和换绑。
5. 给含成员资料的库设置默认私有 Git 策略，在首笔私有写入前成组保护 `records/`、`transactions/`、相关附件及含答案的题目版本。提交前检查 Git 暂存后的实际内容，推送前检查待推送历史。若含受保护资料，停止本次平台操作并列出涉及的路径，交由站主处置。迁移清单显式标明“仅结构”或“含数据”。前者在新设备建立空库，后者按已提交事务头和摘要核验记录、事务及引用文件，缺件即报告。加密备份覆盖这些便携数据和必要的私有身份映射，恢复时重建查询 SQLite。[Git 全量提交流程](../../../plugins/git/server/index.ts) · [备份快照](../../../apps/server/backup.ts)

**验证与完成标准。** 两个独立库可建立相同表名、字段标识和记录 ID，并产生不同数据。分别关闭进程、在空运行数据区重建，检查行数、内容摘要、查询结果与回执。以临时 Git 仓库验证未跟踪、已暂存、已跟踪三种状态。对应 A4、A5、A8、A12、A13。

### M4　联表查询与跨表事务

**用户操作与依赖。** 同库联查设备、借用单和成员，一次借出或报名动作同时更新多张表。依赖 M3 的稳定表结构、授权主体和提交点。可参考现有领域查询中按实体类型和 ID 联接记录的做法，在 `packages/core/databases/` 实现通用查询编译与事务执行，在 `apps/server/databases/` 对接 API。两部分可并行开发，随后联测。[现有关联查询](../../../packages/core/to-doo/queries.ts) · [现有授权策略](../../../packages/core/auth/permissions.ts)

1. 提供按库寻址的表定义读取、结构化查询、事务提交和回执读取。建议管理端路径形如 `/api/databases/<dbId>/query` 和 `/api/databases/<dbId>/transactions`。查询输入含主表、要返回的字段、筛选、排序、分页和声明过的关联。服务端按字段 ID 与类型生成受限表达式，值使用绑定参数。游标绑定库 ID、数据版本、排序、查询和授权版本，以稳定记录 ID 处理排序并列。
2. 在查询规划时对主表、每个关联目标、过滤或排序字段及每一侧的记录分别应用权限，随后计算条数和分页。一对多经引用字段联接，多对多可使用显式关联表。关联目标、事务成员或游标属于其他库时拒绝操作。给常用过滤和联接键建索引，用 `EXPLAIN QUERY PLAN` 与稳定排序的预期结果验证。
3. 写入口接受单项变更或一个已定义的业务动作。动作由可校验的前置条件和新增、更新、删除等操作组成，示例应用负责配置借用、名额及评分规则。服务端决定归属、时间和计算字段。取得库锁后，先核对当前权限，再按库、调用主体及请求 ID 查回执。相同请求指纹可复用，异指纹冲突。新请求须对全部成员验证权限、关联、业务条件和预期版本，回执读取也遵守当前授权。

以下为建议的 API 契约样例。设备、成员、表和字段在同一库的定义中解析。查询后返回授权字段和续页游标，提交后返回事务 ID、记录 ID、结果版本及回执。网站从服务器会话确定成员身份。

| 用途 | 请求正文示意 |
| --- | --- |
| 查仍在借用的设备，显示借用人，按到期日排序 | `{"from":"loans","include":["deviceId","memberId"],"select":["id","deviceId.name","memberId.name","dueDate"],"where":{"status":{"eq":"open"}},"orderBy":[["dueDate","asc"],["id","asc"]],"limit":20}` |
| 提交一次借出动作 | `{"action":"borrowDevice","requestId":"borrow-42","input":{"deviceId":"D-07","dueDate":"2026-12-01"},"expected":[{"table":"devices","id":"D-07","revision":"r7"}]}` |

**借出设备的提交界限。** 在库内写锁中读取设备版本和可借状态，校验借用人，再准备“设备改为已借出”和“新增借用单”两个结果。一次性持久写入包含二者的事务文件，随后整组回放到 SQLite。两名成员并发借同一台设备时，后取得锁的一方重读最新状态并收到冲突。故障位置决定恢复结果：

| 故障或重试发生的位置 | 应看到的结果 |
| --- | --- |
| 权限、设备状态或版本检查失败，或进程在事务文件完成原子落盘之前被终止 | 本次无持久提交。重新打开后，设备和借用单都保持上个完整业务状态。 |
| 事务文件已落盘，SQLite 或当前记录文件尚未全部就绪 | 已有持久提交。重启先按事务 ID 补齐，读者只看到完整事务前或完整事务后的业务视图。 |
| SQLite 已应用，成功响应在网络中丢失 | 同一获授权主体用相同请求重试，取得原借用单和回执。新请求再次借用则因状态冲突失败。 |

**验证与完成标准。** 使用两个独立客户端和并发数据库连接，验证一次成功、一次冲突。分别在提交点前、提交点后和回包前三处注入中断，重启后比对设备、借用单、回执及再执行结果。用活动报名验证同样的机制可扣余位并拒绝重复报名。对应 A5–A9。

### M5　站点绑定、成员、API 与 MCP

**用户操作与依赖。** 网站可绑定已有库或一键建专库，站主及受邀成员可跨设备使用各自的数据。独立库也能通过获授权的 API 或 MCP 使用。资源搜索依赖 M2，库工具依赖 M3、M4，完整绑定和示例站在两线汇合后验收。

1. 在宿主私有元数据中按站点约束最多一条活动绑定，保存库、表、动作、记录范围和授权代次。创建专库并绑定共用一个请求 ID。若只完成建库，重试复用该库并完成绑定，绑定生效前不给站点数据权限。切库或解绑时失效旧凭据、游标及读取句柄。站点页显示授权范围，库详情列出引用它的站点。
2. 默认主人使用。管理端按站点签发一次性、有期限的邀请，接受者设置本站登录凭据，跨设备登录仍关联同一稳定成员 ID。主人从管理端进入交互站点用一次性、限定目标站的登录交接。私有数据站点使用独立来源、限主机的会话和写请求来源校验，资源共享域只读。网站从同源数据入口访问，服务端按站点会话解析绑定。独立 API 客户端使用受库授权的版本化路由组，单独验证令牌用途、动作、范围与撤销代次。以未安装 MCP 的实例验证该路径。密码验证材料、令牌摘要及会话存放在宿主私有运行区。[现有认证边界](../../../apps/server/app.ts) · [客户端密钥管理参考](../../../apps/server/platform/mcp-api-keys.ts)
3. 给 MCP 增加“检索选中发布目录”“读取选中库数据”“写入选中库数据”三类可撤销能力。贯通 [SDK 宿主接口](../../../packages/plugin-sdk/index.ts)、[插件能力与版本检查](../../../apps/server/plugins/host.ts)、[插件清单](../../../plugins/mcp/manifest.json)、[授权上限](../../../packages/core/auth/grants.ts)、[可选资源清单](../../../apps/server/platform/mcp-permissions.ts)和[研究对象契约](../../../plugins/mcp/server/contracts.ts)。结构化库工具显式读表定义、查询、提交和取回执，复用 REST 的授权与事务服务。新增宿主能力时验证老插件在新宿主上的既有工具，旧宿主按声明的版本范围运行或提示升级。既有凭据升级后只继承原授权。
4. 将通用 `search` 的固定知识库读取门槛改为按来源准入，只调用当前连接获权的来源。研究对象增加发布资源类型，`fetch` 按签名类型再次核对授权，句柄绑定连接、映射 ID、文件版本及权限版本。后台仅为已启用且打开 MCP 开关的映射建索引，查询时先限定连接可见的映射集合。HTML 取可读文本，Markdown、TXT 取正文，JS/CSS、图片等仅按文件名与路径匹配，读取这类命中时返回文件元数据和链接。监控新增、修改、删除，Git 拉取后调度刷新，启动及周期对账覆盖漏报。返回结果或正文前复核映射、文件版本及当前授权，停用和撤权立即阻止旧发布句柄读取。私有库记录使用独立的结构化查询工具。[多来源检索接线](../../../plugins/mcp/server/service.ts) · [现有监控调度](../../../packages/core/indexing/watcher.ts)
5. 交付可放入知识库的学习示例站。在个人与受邀成员两种模式下提交答卷，每次记录服务端评分、作答选择和当时的题目版本。同版题目可共用一份不可变内容。修改当前题库后仍能复核历史。恢复到新位置后保留可核对的数据和成员归属，外部映射、库绑定、会话、邀请和远程授权按恢复策略重置，站主核验后重新启用。

**验证与完成标准。** 用互相独立的浏览器会话、直接 API 客户端和最小权限 MCP 连接验证成功路径及拒绝路径。分别撤销目录检索权、数据写权、站点绑定和成员资格，检查下一次调用及旧句柄。备份与恢复使用隔离目标和临时身份。对应 A1、A3、A10–A14。

## 4. 集成与验证顺序

- **并行安排。** M1 固定标识、页面状态与 API 边界后，M2 与 M3 分头推进。M4 的查询与事务分别开发，共用库身份、权限谓词和版本。M2 完成后，M5 的资源索引可以与 M4 并行。M5 的权限类型和测试夹具可提前准备，真实站点读写联测等待 M2、M4。
- **回归入口。** 使用临时知识库和运行数据做 `npm test -- <测试文件>`，前端以 `npm run test:e2e -- <spec>` 验证桌面及手机。可扩展[便携文件测试](../../../tests/knowledge-data.test.ts)、[事务恢复测试](../../../tests/to-doo-store.test.ts)、[权限交集测试](../../../tests/domain-permissions.test.ts)、[MCP 多来源测试](../../../tests/mcp-office-research.test.ts)和[备份边界测试](../../../tests/platform-backup-boundaries.test.ts)。新领域另建发布监听、独立库、并发恢复及端到端用例。最终集成再做 `npm run typecheck`、`npm run build` 和主应用、博客、既有 MCP 工具的回归。
- **交接证据。** 每个用例保留执行版本、夹具、步骤、实际结果及回执或查询断言。浏览器截图证明导航和可见范围，持久性使用重启、磁盘数据与回放结果证明。发布监听和学习站分别记录本机访问端口、运行账户、数据位置及恢复方法，进入后续部署阶段时再配置实际域名和证书。
