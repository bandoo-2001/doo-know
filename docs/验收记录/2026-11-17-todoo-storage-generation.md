# ToDoo 数据写入兼容代次 7

## 实证与影响

使用本机原生 rc68 的真实已编译 schema、codec、ToDoo service 和管理 CLI，在 OS 临时知识库与数据库中核对新数据。没有连接主服务，也没有读取或修改其业务数据。

新版 service 正常创建以下四组数据，再交给旧版读取、改名和保存：

| 数据 | rc68 读取 / 保存 |
| --- | --- |
| 普通清单，包含新版默认 `parentId` / `icon` 字段 | 严格 schema 拒绝 |
| 带上级与自定义图标的子清单 | 严格 schema 拒绝 |
| 像素主题纪念日 | 旧主题枚举拒绝 |
| 自定义图片纪念日，含位置与缩放 | 旧主题枚举及图片字段拒绝 |

四组数据均由新版 schema 接受。旧版真实 ToDoo service 的读取、改名保存流程返回 400 / `TO_DOO_INVALID`，原始文件保持不变；没有发生静默删除新字段。但同一份新数据对应的数据库副本，运行 rc68 原生 `manage self-check` 仍返回 0 / `check: ok`：该自检检查认证、插件与 SQLite 一致性，没有加载延迟初始化的 ToDoo store。因此不能依赖现有健康探测判定旧程序能够使用这些数据。

## 最小修正

发行清单 `databaseCompatibility` 与开发环境的缺省值统一设为 **7**。不重写已有用户文件，不增加无关 SQLite 迁移。现有普通回滚流程在创建管理事务、停止服务或写入数据之前，拒绝从代次 7 回到代次 6；同代次 7 的普通回滚和中断恢复继续有效。

这与宿主 API 1.5 / MCP 2.0.4 的插件安装围栏各自生效。即使没有安装 MCP，原生程序也应保护知识库的新数据。旧 rc68 的正常升级入口允许兼容代次增加，6 → 7 的真实原生升级仍须在独立旧安装中验收。

如确需使用较旧程序，应将升级前的一致性备份恢复到新的空目录并核对，再明确处理升级后新增内容；不能把旧程序直接指向当前知识库。

## 验证

- 真实 rc68 临时数据试验：四组 schema / codec 均拒绝新字段；真实旧 ToDoo 读写拒绝；旧原生自检错误放行的边界成功复现；两次原始文件 hash 均不变；临时目录已删除。
- 源码回归：发行兼容、真实回滚服务边界、回滚中断恢复、升级方向检查共 **4 文件、52 测试通过**。新增代次 7 → 6 测试验证不调用 stop/start、不创建管理数据库、原文与 ToDoo 实体及便携文件不变；同代次 7 测试验证回滚及中断恢复均保留最新记录。
- 原始记录：原始工作区 `.local/production-readiness/legacy-todoo-storage-compatibility.json`；当前工作区 `.local/production-readiness/generation-seven-regressions.log`。

正式 candidate 与恢复包必须从干净提交重建，并确认各自发行元数据均为代次 7。以上临时试验和源码测试不代替最终原生安装验收。
