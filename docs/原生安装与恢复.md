# DooKnow 原生安装与恢复

适用首版 Linux x86_64、glibc ≥ 2.34、systemd 用户服务；验收环境为 Ubuntu 22.04 与 Debian 12。应用、插件及检索发行制品已公开，默认下载不需要Token。下列 `<安装源>` 须替换为自己控制的 HTTPS 制品目录；本机验收允许环回 HTTP。

当前官方公开分发使用 GitHub Releases，可复制的匿名 curl/wget 命令及可选私有认证见[GitHub 安装与发布](私有GitHub安装与发布.md)。下文的普通制品目录方式继续支持。

```bash
curl -fsSL '<安装源>/install.sh' | bash
# 或
wget -qO- '<安装源>/install.sh' | bash
```

安装器下载固定发行包并校验 SHA-256，包含固定 Node 22.22.1、Web、服务端和生产依赖。客户端无需 npm、编译器、全局 Node/Python、Docker 或 sudo。官方 MCP、Git 是独立预构建插件包；检索包按需下载。

安装时从 `/dev/tty` 读取用户名与隐藏密码，新密码至少需要 8 个字符并确认；已有账号仍可使用原密码登录。无终端时不创建账号，输出可在本机终端继续初始化的完整命令。端口占用会终止安装。重跑同一版本保留账号、配置、密钥和数据库；已有安装的版本变化走受控升级。

默认监听 `127.0.0.1:5173`。登录后可只填名称创建知识库，或浏览并选择部署设备上已有的资料文件夹。完整路径和时区放在高级设置中。新建不会预建分类；主动导入 Markdown 时才创建资料目录。知识库、安装、数据库及密钥目录必须分开；不接受软链接。首次设置推荐浏览器时区（无法识别时使用 `Asia/Shanghai`），插件和检索可以稍后准备。

## 安装位置与服务

| 内容 | 默认位置 |
| --- | --- |
| 管理命令 | `~/.local/bin/dooknow` |
| 配置、认证和插件密钥 | `~/.config/doo-know/` |
| 版本、插件、数据、检索运行时、模型、备份 | `~/.local/share/doo-know/` 下分别保存 |
| 下载缓存 | `~/.cache/doo-know/` |
| 日志 | `journalctl --user -u doo-know.service` |

用户服务以前台 `serve` 运行，工作目录 `/`；程序通过发行目录和配置中的绝对路径定位资产。服务停止最多等待 120 秒以排空写入。一个数据目录只允许一套服务实例；独立文件和索引 worker 也登记进程身份，管理操作会拒绝未停止的外部数据进程。

默认服务名 `doo-know.service`。同一用户安装多套时，为每套提供独立配置、数据目录、端口、安装目录和 `--service-name`。管理命令仅控制标记为本配置的用户服务。未启用 linger 时，安装器报告用户会话限制；不会自行提权或宣称无人登录时已经开机常驻。

安装器可通过 `DOOKNOW_PROFILE`、`DOOKNOW_INSTALL_ROOT`、`DOOKNOW_BIN_DIR`、`DOOKNOW_PORT`、`DOOKNOW_APP_ORIGIN`、`DOOKNOW_ALLOW_ROOT`、`DOOKNOW_SERVICE_NAME` 指定环境。显式 `DOOKNOW_NO_SERVICE=1` 安装前台版本，此时用 `dooknow serve` 运行。管理命令会固化安装时的配置、XDG 配置目录和程序目录，重新开终端后仍指向同一实例；独立实例使用不同的配置、程序目录、管理命令目录和端口。旧版命令升级时，新版候选迁移会根据显式传入的可信配置写入程序目录的归属记录，旧启动脚本随后也能在新终端找到该配置。升级前若自定义安装的环境已丢失且尚无归属记录，应加 `--profile <原配置文件>`；不能自动推断其他实例。

## 管理命令

```bash
dooknow status
dooknow doctor
dooknow start
dooknow stop
dooknow restart
dooknow reset-password
dooknow update [--source '<安装源>'] [--version '1.1.0-rc.19']
dooknow rollback
dooknow uninstall
```

`--profile /绝对路径/profile.json` 可用于每条管理命令。卸载移除程序和本配置的用户服务，保留知识库、数据库、插件数据、模型、配置和备份。

`/healthz` 返回控制面、实际代码版本、阶段和维护状态；`/readyz` 表示知识库可用。没有模型不影响浏览和编辑。

`dooknow update` 默认选择最新已发布版本，包含 RC，排除草稿；`--version` 固定到指定版本。更新命令优先使用当前终端的 HTTP(S) 代理及 NO_PROXY；安装或升级时会为本实例记住不含账号密码的代理，后续新终端中的更新可直接复用。无显式或已保存代理时直连。网络超时、代理拒绝连接、DNS、证书、权限或限流错误会给出对应中文说明。

保存的下载代理位于 `<profileFile>.download-proxy.json`，权限为 600，按配置文件隔离。认证代理不会自动保存。显式环境变量优先于保存的设置；可用 `DOOKNOW_NO_SAVED_PROXY=1 dooknow update` 临时忽略保存设置。本机制只为更新命令恢复下载代理，不修改全局 shell 或 systemd 环境。

升级先下载和校验、在数据库副本上自检，再停服、维护、加密备份、迁移、切换和检查新版本。新服务健康后才恢复写入。升级阶段持久记录在安装目录 `update-transaction.json`，并发管理通过独立管理数据库串行化。失败发生在接受新写入之前时可恢复加密数据库快照；一旦到达 `accepted`，禁止自动覆盖新数据。

失败恢复也先持久化 `recoveryAccepted`，再解除维护；重试该阶段只做收尾，不能再次覆盖数据库。快照解密使用随机独占临时文件，验证和同步落盘后原子替换；历史遗留的未完成临时文件不阻塞重试。

上一版本保留。数据库兼容编号相同且旧版本自检成功时，`rollback` 仅回退代码，保留升级后写入。不兼容的迁移需要明确的数据恢复，不能套用旧数据库覆盖新资料。前台模式升级前先正常停止服务，离线自检成功后切换代码，随后自行运行 `serve`。

## 加密备份与空目录恢复

```bash
dooknow backup --destination '/受控目录/knowledge.dooknow'
dooknow restore \
  --source '/受控目录/knowledge.dooknow' \
  --key-file '/受控目录/backup-key.pem' \
  --profile '/新位置/config/profile.json' \
  --data-root '/新位置/data' \
  --knowledge-root '/新位置/knowledge'
```

备份包含原文与隐藏回收站、SQLite 一致性副本、历史、写入核对保全材料（reconciliation）、官方插件包及数据、必要配置和认证材料，整体使用 X25519 / HKDF / AES-256-GCM 加密。恢复私钥默认位于配置旁的 `secrets/backup-key.pem`，不在备份内部；命令仅输出位置与公钥指纹。应将该私钥另行受控保存，否则无法恢复。

备份期间暂停应用写入，并比较原文前后清单；外部编辑器仍可能改变文件，发现变化会拒绝这份备份。大模型和可重建索引不属于备份内容。

恢复拒绝覆盖已有配置或非空目标；原文、数据、插件和配置目录须彼此独立。归档经过认证、校验和路径检查后才复制。复制中断时不激活配置，保留目标资料和 `restore-*.json` 回执供核对；选择新的空目录重试。

恢复保留笔记 ID、历史和附件关系，重新绑定真实根目录，撤销旧会话、分享、OAuth 和静态远程授权。插件配置保留但先停用，检索需要重新准备。恢复结果输出摘要。随后从原安装来源重新运行安装器，设置 `DOOKNOW_PROFILE` 为恢复后的配置，并使用新的 `DOOKNOW_INSTALL_ROOT` 和 `DOOKNOW_BIN_DIR`。先用 `DOOKNOW_NO_SERVICE=1` 和独立端口验证恢复实例；登录检查原文、附件和历史，并重新授权插件，再按实际情况安排服务切换。每个安装目录绑定一个配置，不复用原实例的程序目录来接管另一个配置。目录改名使用专门的身份比较迁移，不使用普通 restore。

## 私有制品构建与验收

```bash
python3 scripts/build-search-runtime.py --help
node scripts/release.mjs --output .local/releases \
  --base-url 'https://<受控制品主机>/<私有路径>' --version '1.1.0-rc.2'
```

构建机准备已锁定并校验的 Node、CPython、模型及 wheelhouse。发行生成 `release.txt`、版本清单、安装器、主程序包、插件目录与独立检索包；源仓库及制品不自动公开。主包保留 Node LICENSE 和构建输入的第三方许可说明。

实际验收版本、命令和结果另记交付记录。Ubuntu／Debian 根文件系统的网络隔离验证可证明用户态运行时兼容；完整 systemd 安装及失败恢复另用独立用户服务验证。标准 ChatGPT OAuth 还需要浏览器可达的 HTTPS 授权站点与 MCP 地址，本机模拟不替代实际客户端验收。

## 既有 Bridge 与原文目录接管

原文改名与平台升级分开进行。保留旧固定发布，停止入口写入和相关 worker，完成一致性加密备份，再用管理工具进行同文件系统改名：

```bash
node dist/server/scripts/rebind-root.js \
  --from '/原知识库目录' --to '/新知识库目录' \
  --env-file '/受控配置/app.env' --journal '/受控目录/root-migration.json' \
  --verify-module '/旧固定发布/dist/server/server/indexing/reconcile.js' \
  --require-stopped '原Web.service' --require-stopped '原Vector.service' \
  --require-stopped '原Bridge.service' --require-stopped '原Tunnel.service'
```

工具不调用新版本数据库迁移。它检查原字符串、真实路径、设备与 inode，拒绝目标占用、跨文件系统、未排空的任务和活跃数据进程；事务比较更新根身份恰好一行。已有平台绑定同时比较更新版本。固定发布的 `assertRoot` 校验与业务元数据摘要通过后才提交，配置失败时移动同一目录回原处，保留其中资料。发生进程崩溃时先核对迁移日志、两处路径和数据库原值，不启动服务或套用普通 restore。

路径改名通过旧发布验收之后，才安装新平台并迁移数据库。Bridge 适配由 `scripts/adopt-bridge.js` 从明确指定的受控配置、Token 清单和 Tunnel 环境文件承接；凭据不进入命令参数、源码或输出。它核对原签发时间、撤销、有效期及 Web/Bridge 两侧策略交集，保留原 Principal/clientId 幂等归属，创建独立管理 owner 映射和密钥引用。已失效凭据不会在导入时重新签发。

可先使用独立环回端口验证新 MCP 与真实 Tunnel，再停用旧 Bridge。标准 OAuth 不接受旧静态密钥。保留旧源码、release、配置和最新资料作为恢复路径，不能用旧数据库覆盖切换期间的合法新写入。

私有制品可由 `scripts/serve-artifacts.js --directory <受控制品目录> --port 3181` 在 `127.0.0.1` 提供；它仅开放安装器、发行清单和普通制品文件，拒绝链接、其他文件和写入方法。通过自己的受控网络或 SSH 转发接入，不自动建立公网下载站点。
